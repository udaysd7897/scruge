# Let marketplaces classify, let codes identify

Most of the brittle rules in the app can go, because the three marketplaces already state most of what those rules try to infer. Every Flipkart page labels the product's vertical in machine-readable form: JSON-LD `category`, `analyticsData.vertical`, an FSN prefix (`MOB…` or `TVS…`) and the image-CDN path. Amazon does the same through its breadcrumb, the bestseller browse-node ID (1805560031 = Smartphones) and `Item Type Name`. Croma has breadcrumbs and category codes in detail mode. A per-brand regex of phone names should therefore be the last resort, not the main path. Identity then splits by category. For **TVs**, the manufacturer model code (LG `55NU870BPLA`, Sony `K-55XR35M2`) identifies the variant on its own and appears on all three platforms, so it should be the primary key. For **phones**, the model number (`CPH2745`, `SM-S948B`, Apple A-numbers) names the model and region only, and Amazon's Samsung and OnePlus listings carry no model number at all. The phone variant therefore has to be rebuilt from structured RAM, storage and colour fields. An LLM is useful here as a cached, schema-constrained normaliser whose every value must quote evidence found in the source. It should not be the judge of whether two listings match. Retrieval should search for the model and then expand to its sibling variants instead of paging deeper through search results. Real captures contain traps that a deterministic layer has to catch: copied model numbers, truncated EANs, bullets that name a sibling model, and junk RAM values. The design should be held to MATCH precision of about 0.98 or better on a hard-negative golden set built from recorded fixtures. Everything below is grounded in the app's own fixtures and code. None of it has been benchmarked on live traffic yet.

## Marketplaces already label the category, and the iPhone shows where that stops

The current `detect_category` in [app/extract.py](file:///Users/sid/scruge/app/extract.py) reads the breadcrumb and then falls back to a hand-maintained title regex of phone lines (`iphone\s*\d{1,2}|galaxy\s+…|pixel…|oneplus…|redmi…|poco…|vivo…|oppo…|realme…|iqoo…|moto…|nothing\s*phone`). The fallback exists because of one real capture. The Apify Amazon item for the iPhone 17 Pro (B0FQG1LPVF) arrives with an **empty `breadCrumbs`, a null `bestsellerRanks`, no "Best Sellers Rank" text and no `Item Type Name`**: none of Amazon's category fields is present ([amz_iphone17pro.json](file:///Users/sid/scruge/tests/fixtures/amz_iphone17pro.json)). The regex fixes that one case and creates an ongoing maintenance job, because every new line (Galaxy XCover, Lava Agni, CMF Phone) needs another entry. It also tends to mislabel accessories, since "Spigen case for iPhone 17 Pro" matches the iPhone pattern.

The structured signals are richer than the code assumes. On Amazon, `breadCrumbs` is present in 7 of 8 captured items, the free-text "Best Sellers Rank" attribute in 7 of 8, and `Item Type Name` in 6 of 8 (always "Smartphone" for phones). `bestsellerRanks[].url` holds the **leaf browse-node ID 1805560031 = Smartphones**, which stays the same as models change ([amz_apify.json](file:///Users/sid/scruge/tests/fixtures/amz_apify.json), [amz_golden.json](file:///Users/sid/scruge/tests/fixtures/amz_golden.json)). On Flipkart, all eight fixtures carry JSON-LD `category` (`mobile`, `television`, `t_shirt`), and full pages also carry `analyticsData` with `vertical: Handset` for phones. Accessories on the same page are labelled separately: `MobileBodyPanel`, `CameraLensProtector` and `MobileChargingMobileCharger`, under the superCategories `RestOfMobileAccessory` and `MobileProtection` ([fk_s26.html](file:///Users/sid/scruge/tests/fixtures/fk_s26.html)). A live check on 12 November 2026 found the pattern holds at scale. The Mobiles browse page returned **199 PIDs, all `MOB…`**, and the Televisions page returned **139 PIDs, all `TVS…`**, with `vertical: Television` under superCategory `HomeEntertainmentLarge` ([Flipkart mobiles](https://www.flipkart.com/mobiles/pr?sid=tyy,4io), [Flipkart televisions](https://www.flipkart.com/televisions/pr?sid=ckf,czl)). Flipkart documents the FSN only as a unique identifier "similar to ISBN" and does not document the prefix as a category code ([Flipkart seller docs](https://seller.flipkart.com/api-docs/FMPlatOverview.html)). The prefix should therefore serve as a cross-check, not as the authority. Croma's detail mode gives `breadcrumbs = Phones & Wearables > Mobile Phones > Android Phones` and `category_l0/l1/l2 = 1/10/95`. Its search-mode ("golden") items have neither, only a short `specs` subset and a URL slug ([croma_apify.json](file:///Users/sid/scruge/tests/fixtures/croma_apify.json), [croma_golden.json](file:///Users/sid/scruge/tests/fixtures/croma_golden.json)).

The recommended detector has five layers, and the first three need no model names. **Layer 1** reads the marketplace-assigned category: the Amazon node-ID whitelist and then the leaf text, Flipkart's JSON-LD `category` or `analyticsData.vertical`, and Croma's breadcrumb text (safer than its numeric codes, which have only one observed value). **Layer 2** reads codes: the Flipkart PID prefix, the image-path vertical slug, and Amazon `Item Type Name` normalised to "smartphone" or containing "tv/television". **Layer 3** is a spec fingerprint. A phone has OS ∈ {iOS, Android}, a storage capacity, weight under about 350 g and thickness under about 1.5 cm. A TV has any of HDMI port count, tuner type, VESA mount or display size class of 24 inches or more. The iPhone capture passes layer 3 with no name lookup: its `productOverview` shows **Operating System = iOS and 256 GB storage, and its dimensions are 0.87 cm and 206 g** ([amz_iphone17pro.json](file:///Users/sid/scruge/tests/fixtures/amz_iphone17pro.json)). An iPad would also show iOS but weighs over 400 g with a screen of 8 inches or more, which is why the weight bound matters. **Layer 4** is a constrained classifier for whatever remains: an LLM call or an embedding nearest-centroid model, with a closed label set `{smartphone, television, phone_accessory, tv_accessory, other}`. **Layer 5** returns unsupported.

Making the accessory classes explicit removes the main failure mode, and it matches how every taxonomy examined treats accessories. Google files phone cases (2353), screen protectors (5468) and TV mounts (4458) in branches separate from Mobile Phones (267) and Televisions (404) ([Google taxonomy](https://www.google.com/basepages/producttype/taxonomy-with-ids.en-US.txt)). Shopify's production classifier, which handles 30M+ predictions a day, also validates model output against taxonomy rules and routes disagreements to judge models ([Shopify Engineering](https://shopify.engineering/evolution-product-classification)). Constraining the output to an enum also guards against the "inflation" failure seen in zero-shot LLM categorisation, where models invent categories ([arXiv 2510.13885](https://arxiv.org/html/2510.13885v1)). A three-way decision with an accessory trap is far easier than the full-taxonomy title classification behind the familiar ~0.85 weighted-F1 figures ([Rakuten Data Challenge](https://sigir-ecom.github.io/ecom2018/data-task.html)). The bigger gain comes from a different source: layers 1 and 2 produce labels for free. Every Flipkart `MOB`/`TVS` item and every Croma breadcrumb is a correctly labelled training example for the layer-4 embedding classifier, and every capture is a regression test. Two parts of this layering are still unproven. No accessory fixture exists on disk, and no Croma TV detail item exists either, so the accessory guards and Croma's TV breadcrumb strings are both untested.

## Phone codes name the model; TV codes name the variant

Treating "model number" as one concept across categories is the most consequential design error available here. The fixtures show the split clearly. Every OnePlus 15 variant at Croma (12+256 in Sand Storm, Infinite Black and Ultra Violet, and 16+512 Infinite Black) carries the **same `Model Number = CPH2745`** ([croma_golden.json](file:///Users/sid/scruge/tests/fixtures/croma_golden.json)). Apple's A-numbers are assigned per model and region group, so the iPhone 17 Pro is A3523 in "other countries and regions" and A3256 in the US, whatever the storage or colour ([Apple support](https://support.apple.com/en-in/108044)). Only two kinds of phone code are true per-variant SKUs. The first is the Apple part number, which Amazon exposes as `Item model number = MG8H4HN/A` and whose `HN` is the community-documented India region code ([gist](https://gist.github.com/donn/0c501ab625625c381fdf3210bf0ff275)). The second is the full Samsung code. In Croma's S26 Ultra captures the base `SM-S948B` is constant and a three-letter block varies: `ZVB` Cobalt Violet 256 GB, `LBB` Sky Blue 256 GB, `ZWB` White 256 GB, `ZKC` Black 512 GB ([croma_apify.json](file:///Users/sid/scruge/tests/fixtures/croma_apify.json)). That block looks like colour plus storage tier. The S24's 256 GB code ends in `W` rather than `B`, though, so the letter meaning depends on the model. The full codes should be compared for equality and never decoded with a fixed table, a conclusion consistent with Samsung publishing no universal decoder ([itechguides](https://www.itechguides.com/what-do-samsung-galaxy-model-numbers-mean-a-simple-guide/)).

TVs work the other way. LG model codes begin with the screen size, followed by series, region and design letters ([Trusted Reviews](https://www.trustedreviews.com/news/what-do-the-lg-tv-product-codes-mean-4038909)). Sony India uses India-only `K-` codes such as K-43S22M2 ([Sony India](https://www.sony.co.in/electronics/support/articles/00409057)). One generic pattern, `^(?:[A-Z]{1,5}-?)?(\d{2,3})([A-Z].*)$`, extracts size and series core from every TV code in the fixtures: `55NU870BPLA`, `55UA82006LA`, `OLED55C6XLA`, `K-55XR35M2` and `55UR75006LC.ATR`. The dotted suffix has to be stripped first. The code appears in Amazon's Model Name, Model Number and Manufacturer Part Number, in Flipkart's "Model Name" spec, and in Croma's "Model Number" ([amz_golden.json](file:///Users/sid/scruge/tests/fixtures/amz_golden.json), [fk_tv_lg_nu870.html](file:///Users/sid/scruge/tests/fixtures/fk_tv_lg_nu870.html)). **Exact equality of the normalised full TV code is close to a sufficient match key**, and the parsed size is a consistency check against the "Screen Size" field. The suffix still matters: an earlier finding showed that LG's 55UQ8020PSB and 55UQ8040PSB are different models, so trailing characters must not be stripped blindly. Store marketing names ("NU87 Nano", "AI TV UA8200") become aliases to resolve and should never act as identity.

Identifier coverage across the three platforms is uneven, and the matcher has to be designed around that.

| Identifier | Amazon.in (Apify) | Flipkart (HTML) | Croma (Apify) |
|---|---|---|---|
| EAN/GTIN | Absent in every phone/TV capture | Absent; JSON-LD `sku` is the internal FSN | `ean` on every item, some malformed |
| Phone model code | Absent for Samsung and OnePlus; iPhone has part number `MG8H4HN/A` | "Model Number", sometimes base (`SM-S948B`), sometimes full (`SM-S921EZAWINS`) | Full Samsung SKU; `CPH2745` for OnePlus |
| TV model code | Model Name / Model Number / MPN | "Model Name" in `__INITIAL_STATE__` specs | "Model Number" |
| RAM / storage | Structured attributes; variantAttributes | "RAM", "Internal Storage" | "RAM", "Internal Storage" |

Sources: [amz_apify.json](file:///Users/sid/scruge/tests/fixtures/amz_apify.json), [fk_pdp.html](file:///Users/sid/scruge/tests/fixtures/fk_pdp.html), [fk_s26_512blk.html](file:///Users/sid/scruge/tests/fixtures/fk_s26_512blk.html), [croma_golden.json](file:///Users/sid/scruge/tests/fixtures/croma_golden.json).

The table leads to a practical rule. Amazon→Flipkart/Croma phone matching for Android brands cannot use codes at all, because Amazon carries none. It has to use brand, normalised model name with the tier set, RAM, storage and colour. Croma↔Flipkart can join on the Samsung base code. EAN accelerates matching but cannot be the primary join, since only Croma exposes it. Each colour and storage gets its own EAN (the four S26 Ultra variants end …162, …193, …773 and …902), so a validated EAN match means the same variant. Free external GTIN lookup adds little. GS1 India's validator is free per lookup but was originally limited to India-issued GTINs, and roughly 15% of BigBasket's queries failed because the GTINs were issued abroad ([GS1 India](https://gs1india.org/gtin-validation/), [GS1 UK](https://www.gs1uk.org/insights/news/GS1India-building-trust-and-boosting-efficiency-with-verified-product-data)). Samsung, LG, Sony and OnePlus EANs are Korean, Japanese or Chinese issues. GSMArena now redirects automated access to a TollBit pay-per-crawl gateway ([gsmarena terms](https://www.gsmarena.com/terms.php3)). In practice Croma is the free canonical catalogue: it already pairs model number, model series, RAM, storage, colour and EAN for each SKU.

### LLM extraction earns its place only behind evidence checks

LLMs extract product attributes well. GPT-4 reaches about **91 F1 on WDC-PAVE, roughly 10 points above the best pre-LLM extractors**, and unit conversion is the hardest part of normalisation ([Brinkmann et al.](https://arxiv.org/abs/2403.02130v4)). The same model family fails in a predictable way when used as a matcher. In entity matching, GPT-4's errors come mostly from **overweighting shared attributes and misreading small model-number differences** ([Peeters et al.](https://arxiv.org/html/2310.11244v4)). That is exactly the 128-vs-256 GB and Pro-vs-Pro Max error a stock checker cannot tolerate. The current [app/llm.py](file:///Users/sid/scruge/app/llm.py) asks the LLM the pairwise question, "is it the identical product". That makes it the matcher, which is the wrong job for it.

The LLM's job should be per-listing normalisation, cached by ASIN, FSN or Croma ID plus a hash of the input. Its output is a typed record: `{category, brand, line, generation, tier, model_codes[], ram_gb, storage_gb, screen_in, colour_raw, colour_family}`. Four guardrails make that output safe to use. First, the schema is enforced through JSON-schema or tool output, with enums for storage, RAM and colour family and every field nullable. Second, each field carries an `evidence` substring that code checks verbatim against the input, and a field whose evidence is missing is dropped. Third, the input is ordered as title, then structured specs, then bullets, and bullets are never used for identity fields. Fourth, the LLM output is cross-checked against the deterministic parse, and disagreements go to review. Regex and the spec fields already handle storage, RAM, screen size and most codes. The LLM adds value for model-name canonicalisation ("S26 Ultra 5G" vs "Galaxy S26 Ultra") and for mapping marketing colours to colour families. Cost is negligible. At Claude Haiku 5.5's **$0.10 per million input tokens and $0.50 per million output tokens**, a compacted 1,500-token record costs about $0.0002, and the Batch API halves that ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Gemini 2.5 Flash-Lite is priced similarly ([Google AI pricing](https://aistudio.google.com/docs/pricing)). Sending raw Flipkart HTML, at about 1.6 MB per page, would cost about 100 times more, so the spec table should be extracted before any LLM call. Amazon's 2026 work supports the same split. Its system builds attribute structures with an LLM offline and ranks over them online, which cut tokens by 57% and improved zero-shot precision ([arXiv 2604.27410](https://arxiv.org/pdf/2604.27410)).

## Real captures hide seven traps that break naive extraction

The fixtures hold concrete failures, and any extractor, LLM or regex, will hit them. A golden set should treat each one as a test case.

| Trap | Evidence | Defence |
|---|---|---|
| Copied model number | Croma S26 Ultra **Black** (EAN 8806097852773) has `SM-S948BLBBINS`, the **Sky Blue** code | Title, Brand Color and EAN outrank the code suffix; a suffix conflict alone must not veto |
| Truncated / suffixed EANs | `6921815630548N`, `8806097852605N`; three OnePlus 15 EANs are 12 digits and fail the check digit | Strip a trailing `N`, run the GS1 mod-10 check, and use the EAN as a key only if it passes |
| Bullet names a sibling | iPhone 17 **Pro** bullet: "Ceramic Shield protects the back of iPhone 17 **Pro Max**" | Never read identity from bullets; use title + `Generic Name` + part number |
| Junk RAM | iPhone `productOverview` "RAM Memory Installed Size = **0.1 GB**" | iPhone RAM = null; null is neutral, never a mismatch |
| Commercial pseudo-variants | Amazon variantAttributes "With exchange bonus", "Without Protect+", "Samsung Care" | Drop non-product axes from the variant key |
| Shifted Flipkart specs | In `__INITIAL_STATE__` the value precedes its label | Parse by label index (`label_0` = name), not "label then next text" |
| Decoy capacity | Flipkart "User Available Internal Memory = 479.2 GB" alongside "Internal Storage = 512 GB" | Read only marketed-capacity fields |

Sources: [croma_apify.json](file:///Users/sid/scruge/tests/fixtures/croma_apify.json), [croma_golden.json](file:///Users/sid/scruge/tests/fixtures/croma_golden.json), [amz_iphone17pro.json](file:///Users/sid/scruge/tests/fixtures/amz_iphone17pro.json), [amz_apify.json](file:///Users/sid/scruge/tests/fixtures/amz_apify.json), [fk_s26_512blk.html](file:///Users/sid/scruge/tests/fixtures/fk_s26_512blk.html).

Three normalisation problems sit alongside the traps. Screen sizes come in many forms: one 55-inch set appears as "140 cm", "139.7 cm" and "139 cm" in Croma titles, and the S26 Ultra screen is "6.88" at Croma, "6.9 inch" at Flipkart and "6.9 Inches" at Amazon. The fix is to take the inch value, compare TVs by integer inch and phones within ±0.1", and never compare in cm. Colour needs two tiers. The marketing name is compared first, case-folded and with a Levenshtein distance of 2 or less, which absorbs Croma's "Ultra **Voilet**". The colour family serves only as a weak fallback, because Croma maps "Sand Storm" to WHITE and families collide. Model tiers need set equality over tier tokens `{pro, max, plus, ultra, air, mini, lite, fe, e, neo, prime}` with "5G" dropped. That is what stops "iPhone 17 Pro" from matching as a substring of "iPhone 17 Pro Max". The code already drops 5G in `FAMILY_DROP_TOKENS`. Tier-set equality should replace the substring and overlap tests in `matcher.py`.

## Search for the model, then walk to the exact sibling

Retailer search ranks by relevance and popularity, not by variant. In the Croma S26 Ultra case, search found the right model but ranked the exact storage variant **6th or 7th**. A top-k cut, or a cheaper smaller page, therefore drops the correct answer before the matcher sees it. The fix is structural. Production comparators model products in two levels: Google Merchant Center groups variants under `item_group_id` and names memory and display size as variant-defining for electronics ([Google Merchant Center](https://support.google.com/merchants/answer/6324507?hl=en)). Indian comparators key their pages at model plus RAM/storage, as in 91mobiles' `poco-m8-256gb-8gb-ram-price-in-india` ([91mobiles](https://www.91mobiles.com/poco-m8-256gb-8gb-ram-price-in-india?ty=prices)). Retail product pages follow the same model, with one page per model and variant selectors on it, and that is what makes sibling expansion possible.

The retrieval ladder should stop at the first rung that returns a model-level hit. Rung 1 is the exact manufacturer code (`SM-S948B`, `55NU870BPLA`). Rung 2 is the canonical model name without variant tokens. Rung 3 adds storage, and is used only if the first two find nothing. TV queries use brand + size + series core, never a store's marketing family alone. Among the results, the model-level filter keeps candidates whose `(brand, line, generation, tier)` agree. A null on one side counts as unknown, not as a mismatch. Hard vetoes run **before** any top-k truncation. Then comes the step the app currently lacks. From the best model-level hit, the matcher reads the variant list (Amazon `variantAsins`/`variantDetails`, Flipkart's swatch PIDs, Croma's variant data) and adds each sibling as a candidate. A grep of [app/sources](file:///Users/sid/scruge/app/sources/) finds no reference to variants, EAN or breadcrumbs in any adapter. Sibling expansion should also lower Apify spend, at roughly $0.07 per Croma result: ask for 5 results and make one detail fetch instead of buying 20 results, though how the actor bills detail fetches still has to be checked. A model → retailer-page cache means the second lookup for any S26 Ultra variant skips search entirely. Stock must always be read from the chosen leaf's own page, never from the model page.

The LLM's second job sits here, and its scope is narrow. When two or more survivors remain close after vetoes, one listwise call receives the source record and the survivors' normalised records. It returns an index or "none" and must name the differing field. The deterministic vetoes then run again, so the judge cannot overturn a conflict on storage, RAM, size or code. This copies Shopify's cascade, in which cheap features feed stronger scorers, thresholds are tuned "for precision first", contradiction features block merges, and an LLM labels pairs offline rather than ruling at serving time ([Shopify Engineering](https://shopify.engineering/catalog-clustering-part-ii)). A Google Shopping cluster lookup through SerpApi would give a cross-retailer recall path (250 free searches a month) ([SerpApi pricing](https://serpapi.com/pricing)). Its coverage of Croma and Flipkart in India is unverified, so it remains an option rather than part of the plan.

## Measure retrieval and matching separately, on hard negatives

A single accuracy number would hide where failures happen. WDC Products shows why corner cases need their own measurement: raising their share from 20% to 80% costs models 7–10 F1, and unseen products cost more, with Ditto falling from 79.1 to 68.4 ([WDC Products](https://webdatacommons.org/largescaleproductcorpus/wdc-products/)). Cross-platform lookup is almost always an unseen-product problem. The golden set should be about 40–80 source listings × 3 stores. Each candidate gets a graded label, `exact / same_model_other_variant / same_model_other_colour / different_model / accessory`, and each (source, store) pair gets an expected decision. The required hard negatives are: Pro vs Pro Max; S26 vs S26+ vs S26 Ultra vs S26 FE; 128 vs 256 vs 512 GB; 8/256 vs 12/256; 55" vs 65" of one series; NU87 vs NU85 at the same size; S25 vs S26; the phone vs its case; and refurbished listings. Source-side gaps belong in the set too: the breadcrumb-less iPhone, RAM-less Apple listings, and TVs whose store family name differs from the code.

Four metrics should be reported separately: **retrieval recall@k** (was the exact item fetched at all), **veto false-reject rate**, **MATCH precision** (target ≥ 0.98, in line with the calibrated auto-accept in [arXiv 2608.25037](https://arxiv.org/abs/2608.25037)), and **abstain rate** (cases where an exact item existed but the answer was AMBIGUOUS or NONE). Every stage should be a pure function over recorded HTML/JSON, with LLM outputs frozen into the fixtures. The suite then runs offline, costs nothing and gives the same result every run. An LLM can pre-label new captures and generate further hard negatives ([ICML 2026](https://icml.cc/virtual/2026/71465)), but a human confirms every label, following Shopify's practice of validating the judge against human annotations. No public Indian phone/TV golden set exists, and no published accuracy figure covers 2026 small models on Indian listings. The thresholds above are therefore starting points, and the app's own measurements should replace them.

## The recommended architecture, and what to delete

The pipeline below fits in the existing module layout. Precision is enforced by plain code at the end.

**Data model.** `ProductRecord {store, store_id, url, title, category, brand, line, gen, tier, model_codes[], ram_gb?, storage_gb?, screen_in?, colour_raw?, colour_family?, gtin?, price, stock, evidence{field: span}, siblings[]}`. Identity is `model_key = (brand, line, gen, tier)` and `variant_key = model_key + (ram, storage)` for phones or `model_key + screen_in` (or the full normalised code) for TVs. Colour is a separate comparison, so "same variant, other colour" can be reported as its own outcome.

**Flow.** (1) Category from marketplace fields, then the spec fingerprint, then the constrained classifier. (2) Deterministic parse of the spec tables, then the cached LLM normaliser with evidence checks. (3) A per-store query ladder (code → name → name + storage) with a small result page. (4) Model-level filter. (5) Sibling expansion from the best model hit. (6) Generic vetoes: numeric conflicts on storage, RAM and size; a base-code conflict when both sides have codes; a mismatch on a validated GTIN; a category outside phone/TV. (7) Scoring in the order validated GTIN > full code > attribute agreement > title similarity, with colour as a bonus. (8) Decision: one fully agreeing survivor → MATCH; several → listwise LLM, then re-veto; otherwise AMBIGUOUS. NONE stays distinct from "fetch failed". (9) Stock from the leaf page.

**What to stop hard-coding**, mapped to the current code:

| Hard-coded today | Replace with |
|---|---|
| `_TITLE_RULES` phone-line regex (`iphone…|galaxy…|pixel…|redmi…`) in `extract.py` | Marketplace category fields (node ID 1805560031, Flipkart `vertical`/JSON-LD, Croma breadcrumb) → spec fingerprint → enum classifier with accessory classes |
| `_CRUMB_RULES` keyword matching on breadcrumb text | Leaf equality against a small, data-file whitelist of node IDs and vertical names, harvested from captures |
| Title-keyword `is_accessory` as the main accessory guard | Accessory leaves/verticals (`RestOfMobileAccessory`, `MobileProtection`, Google 2353/5468/4458) plus explicit accessory labels in the classifier; title keywords kept only as a secondary guard |
| Apple special case in `missing_required` | Null-is-neutral semantics in the veto engine for any brand that omits a field |
| `tv_family` / `_tv_family_overlap` heuristics on marketing names | Generic TV code parse (size + series core), full-code equality, and an `aliases.yaml` (`LG NU87 ↔ 55NU870*`) that grows from observed misses |
| Pairwise "identical product?" LLM prompt in `llm.py` | A cached per-listing normaliser with evidence spans, plus an optional listwise tie-breaker that cannot override vetoes |
| Implicit fixed-table code decoding | Equality on full codes; base-prefix join only (`SM-[A-Z]\d{3}[A-Z]?`) |

The few constants that stay in code are generic: unit conversions, the standard TV size list, the tier-token set, the GS1 check digit, and the null-is-neutral rule. Everything brand-specific moves into data that captures can refresh.

## Conclusion

The brittle rules came from treating each marketplace as an unlabelled text source. The captures show the opposite. The marketplaces have already classified the product, and the manufacturers have already named the TV variant. The work left to the app is reading those labels faithfully, and rebuilding the phone variant only where no code carries it. That shifts maintenance in a useful direction. A new phone launch needs no code change, because node IDs, Flipkart verticals and spec fingerprints do not change with model names. A new data quirk becomes a fixture plus a guard rather than another regex alternative.

The less obvious lesson is that phones are the harder category, and the cause is data, not language. TV identity reduces to string equality on a code that all three stores publish. Phone identity on Amazon depends on structured RAM, storage and colour fields, and the captures show those fields are sometimes junk (0.1 GB RAM), polluted (Protect+ "variants") or contradicted by the store's own model number. Precision on phones will therefore depend mostly on how well null, conflicting and decoy values are handled, and less on how clever the extractor is. The golden set should weight its effort accordingly.
