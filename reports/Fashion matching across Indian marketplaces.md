# Bridge through the brand's style code

The most reliable way to recognise the same T-shirt or sneaker across Amazon.in, Flipkart and Myntra is to ignore the titles and match on the **brand's own style code**. Myntra hides that code, so use the brand's website to translate it into the brand's official product name. Amazon.in and Flipkart both publish the code on brand-direct listings. On the Puma tee in question, the value `52885601` appears three times on Amazon (Style Number, Item model number, Manufacturer Part Number) and once on Flipkart (spec row "Style Code") ([Amazon.in B0FGJ6FVZ6](https://www.amazon.in/dp/B0FGJ6FVZ6); [Flipkart TSHHEYWZMK66DDSE](https://www.flipkart.com/x/p/itm?pid=TSHHEYWZMK66DDSE)). Myntra shows no brand code anywhere in its page data. However, its brand-direct titles copy the brand's official name almost word for word: "Puma Train All Day Men Breathable Training Tee" is Puma's own name for style 528856 ([Myntra 35720668](https://www.myntra.com/tshirts/puma/x/35720668/buy); [in.puma.com](https://in.puma.com/in/en/search?q=528856)). No marketplace publicly shows an EAN, so barcodes can't serve as the key. The titles themselves carry almost no identity signal: in Zalando's study of cross-retailer fashion matching, title text alone scored an AUCPR of 0.6 out of 100 ([Zalando, arXiv 2403.11593](https://arxiv.org/html/2403.11593)). Images rank candidates well but do not prove identity, and that limit is sharpest for plain basics. The design that fits ~10–50 candidates per platform on a small budget is a precision-first cascade. It accepts a match outright when the codes agree. When they don't, it uses the brand site to build search queries and a reference image, applies hard attribute vetoes, shortlists by image embeddings, and sends only the top 1–5 pairs to a cheap vision-language model. It returns "not confirmed" whenever the evidence is thin. Expect high precision but limited coverage. Even commercial vendors report apparel match rates of only **40–60%**, against about 95% in electronics ([DataWeave](https://dataweave.com/blog/from-mess-to-match-solving-product-identity-at-retail-scale)).

## Two of three marketplaces publish the style code; Myntra publishes none

Large sportswear brands give every colourway its own stable code, and brand-direct sellers copy it into marketplace fields:

- **Puma:** six-digit style plus two-digit colour. 528856 is the Train All Day tee and 01 is PUMA Black, so `52885601`. On in.puma.com the style is in the URL path and the colour is the `swatch` parameter, and the site lists eight colours of this style ([in.puma.com](https://in.puma.com/in/en/search?q=528856)).
- **Nike:** six characters, a hyphen, then a three-digit colourway (`DH2987-100`). The code ends nike.com/in product URLs. Two codes with the same base and different suffixes are the same shoe in different colours ([nike.com/in](https://www.nike.com/in/t/court-vision-low-next-nature-shoes-N2fFHb/DH2987-101); [underpriced.app](https://www.underpriced.app/tools/nike-style-code-lookup)).
- **Adidas:** a six-character article number, such as `KW4826`.
- **Skechers in India:** style number, an India suffix, then a colour: `999889ID-CHAR` ([Flipkart Skechers](https://www.flipkart.com/skechers-summits-field-day-sneakers-men/p/itmd7d39298e0910?pid=SHOH3PYMJWR2HRGU)).
- **Indian licensees:** these have internal codes too. U.S. Polo Assn. lists `UDTSHC0021` ([Flipkart USPA](https://www.flipkart.com/u-s-polo-assn-solid-men-neck-green-t-shirt/p/itm17e98ab09cd71?pid=TSHGHYTJPHEKHNYH)).

The same fields can also hold rubbish. An unbranded Flipkart seller filled "Style Code" with `LINING-PLUS-HS-PKT-NVY- 5XL`, a seller SKU that even contains the size ([Flipkart SMAN](https://www.flipkart.com/sman-solid-men-polo-neck-navy-blue-t-shirt/p/itm7d3435a6770f9?pid=TSHHR5HCZSHSKH9U)). Amazon's seller documentation likewise warns that part and model numbers are often just the seller's own SKU ([Amazowl](https://wiki.amazowl.com/sop/amazon-foundations/part-model-numbers)). So a value should count as a brand code only if it passes a brand-specific pattern and contains no size token.

| Marketplace | Where the brand code lives | What else to read | Traps |
|---|---|---|---|
| Amazon.in | "Style Number", "Manufacturer Part Number", "Item model number" (all `52885601` on the Puma child ASIN) | "Model Name" (free text, e.g. "M TAD ESSENTIAL Tee"), manufacturer, child-ASIN → [size, colour] map | Parent ASIN `B0FMFDYQXD` spans several colours and therefore several codes. Read the child. Model Name changed between two fetches. Search (`/s?k=`) returned an Akamai bot challenge to plain HTTP ([Amazon.in](https://www.amazon.in/dp/B0FGJ6FVZ6)) |
| Flipkart | Spec row **"Style Code"** (apparel) or **"Article Number"** (footwear), in the page-state JSON. Footwear JSON-LD `description` also ends in the code ("… - DH2987-100") | "Model name" for footwear (e.g. "COURT VISION LO NN"), "Brand Color", manufacturer/packer, Country of Origin. Image filenames such as `xl-52885699-puma-original-…` | JSON-LD `sku` is Flipkart's PID, not the brand code. Page HTML also contains *recommended* products' image filenames ([Flipkart Nike](https://www.flipkart.com/nike-court-vision-lo-nn-sneakers-men/p/itmde6fa6fc67661?pid=SHOGRVJPSM9MFYYE)) |
| Myntra | **Nowhere public.** JSON-LD `sku` and `mpn` are both Myntra's own styleId | Product name (tracks the brand's official name), `baseColour`, MRP, manufacturer/packer/importer, `catalogAttributes` season/year, colour-variant styleIds, size measurements | Numbers in older image filenames are a three-digit prefix plus an upload timestamp, not EANs. `myntra.com/528856` resolves to unrelated Blackberrys trousers ([Myntra](https://www.myntra.com/528856)) |

All six Flipkart pages sampled, four apparel and two footwear, had a Style Code or Article Number row. That is a small sample, but it is consistent. Myntra holds the right fields internally, but they stay in the seller back-end. Its catalogue integration requires a `vendorArticleNumber` and treats GTIN as optional ([Fynd docs](https://documentation.fynd.com/commerce/docs/openapi/listings-management/myntra/attribute-myntra.md)). None of those fields reached the public HTML of five sampled Puma, Nike, Adidas and USPA product pages. Myntra's mobile-app API was not checked and might expose more. No marketplace shows an EAN on a public page. The barcodes do exist: Puma's own product page carries 13-digit variant IDs per size that look like EAN-13s, such as `4069159954134` ([in.puma.com PDP](https://in.puma.com/in/en/pd/train-all-day-essential-mens-t-shirt/528856?swatch=01)). Without a marketplace that shows them, though, they cannot link listings.

Before comparing, normalise every code: uppercase it and strip hyphens, underscores and spaces, so that `528856_01`, `528856-01` and `52885601` become one key. Keep two keys per listing:

- a **full key** (style plus colour) for exact matches
- a **base key** (Puma's first six digits, Nike's code before the hyphen, Skechers' digits before `ID`) for "same style, different colour"

Starting patterns:

- Puma: `^\d{6}[-_ ]?\d{2}$`
- Nike: `^[A-Z]{2}\d{4}-?\d{3}$`
- Adidas: `^[A-Z]{1,2}\d{4,5}$`
- Skechers: `^\d{5,6}[A-Z]{0,3}(-[A-Z]{3,5})?$`

These are working heuristics rather than published formats. Adidas in particular has no official format document. Formats for ASICS, New Balance, Levi's, H&M and the ABFRL brands (Allen Solly, Van Heusen and others) were not verified.

## The brand site turns three unrelated titles into one name

The three Puma titles look unrelated, but each is a different projection of the same brand record. in.puma.com resolves style 528856 to the display name "Train All Day Men's Breathable Training Tee". It also gives colour 01 = "PUMA Black", gender Male, material "Shell: 100% Polyester" and price ₹1,799 ([in.puma.com PDP](https://in.puma.com/in/en/pd/train-all-day-essential-mens-t-shirt/528856?swatch=01)). Its URL slug "train-all-day-essential" explains Amazon's Model Name "TAD ESSENTIAL". Puma's material and colour fields account for Amazon's "Polyester" and Flipkart's "Black". Myntra's title is the display name nearly verbatim. Two softer signals agree as well. The manufacturer string "Aryan Apparels … IMT Manesar" appears on Amazon, Flipkart and Myntra, and the MRP of ₹1,799 is identical on Myntra and Flipkart ([Myntra 35720668](https://www.myntra.com/tshirts/puma/x/35720668/buy); [Flipkart TSHHEYWZMK66DDSE](https://www.flipkart.com/x/p/itm?pid=TSHHEYWZMK66DDSE)).

Marketplace titles are better read as a bag of attributes than as names. Flipkart's sellers cannot edit the title shown on the site, which suggests the platform builds it from attributes ([Scribd Flipkart guide](https://www.scribd.com/document/636096254/Untitled)). That is why "PUMA Printed Men Round Neck Black T-Shirt" says nothing about the product line. The adidas Flipkart title "ADIDAS Solid Men Polo Neck Blue T-Shirt" is just as empty, and its "Brand Color" field holds adidas's internal abbreviation `SIGCYA` ([Flipkart adidas](https://www.flipkart.com/x/p/itm2064871066e94?pid=TSHHJXCPFDZY65DU)). The attributes are also noisy. Amazon calls the Puma tee "Solid" and Flipkart calls it "Printed", so pattern can only be a soft signal. Brand, gender, garment type (tee, polo or jersey) and base colour are reliable enough to act as vetoes.

Text normalisation therefore has four steps:

1. Parse brand, gender, category and colour.
2. Expand line abbreviations through a per-brand dictionary (TAD → Train All Day, Ess → Essentials, Prfrm → Performance), seeded from brand-site names and slugs.
3. Resolve the code on the brand site to get the canonical name and colour name.
4. Compare normalised names, not raw titles.

LLMs are good at the extraction step. GPT-4 extracts and normalises product attributes from titles at about **91% F1** ([Brinkmann et al., arXiv 2403.02130](https://arxiv.org/html/2403.02130v1)). Fine-grained fashion attributes read from images are much weaker: Gemini 2.0 Flash reaches only 56.8% macro-F1 zero-shot ([arXiv 2507.09950](https://arxiv.org/html/2507.09950v2)). Where the brand site is reachable, look the expansion up there rather than letting an LLM guess it. Use the LLM as a fallback and verify what it returns.

The bridge is verified only for Puma India, where a plain request to `in.puma.com/in/en/search?q=528856` returned every colourway. Nike's URLs end in the style code, so nike.com/in can very probably be resolved the same way. Nike's India storefront nike.in, run by Nykaa Fashion, uses its own numeric IDs ([nike.in](https://www.nike.in/nike-court-vision-low-next-nature-men-s-shoes/p/24926271)). Whether adidas, Skechers and the Indian licensees support search by code was not tested. For licensees such as Arvind's USPA it is also unknown whether the same code appears across retailers. For those brands, plan for the bridge to fail sometimes and fall back to image-led matching.

## Images rank candidates well but cannot certify plain basics

The best evidence on image matching comes from Zalando's 2024 study of cross-merchant offer matching. It covered about 2M fashion offers, and over 99% of the offers in the index had no true match ([arXiv 2403.11593](https://arxiv.org/html/2403.11593)). Three results matter for this design. Text alone fails. Zero-shot image embeddings rank well but separate matches from non-matches poorly. And a very small trained head closes most of that gap.

| Method (in-domain) | AUCPR | R@1 | R@3 |
|---|---|---|---|
| CLIP text only + projection | 0.6 | 11.1 | 23.5 |
| DINOv2 ViT-G-14, raw | 2.4 | 22.7 | 32.4 |
| CLIP ViT-bigG-14, raw | 27.2 | 62.9 | 77.9 |
| CLIP image + learned projection | 57.2 | 77.8 | 93.0 |
| fashionID (CLIP image + text + numeric, projected) | **66.1** | **84.2** | **95.2** |

Source: [Zalando, arXiv 2403.11593](https://arxiv.org/html/2403.11593)

The projection head has only **0.6M parameters** and trains in about ten minutes on one A100. Its labels could come from code-matched pairs, which this system produces for free. Off-the-shelf, Marqo-FashionSigLIP leads public fashion retrieval benchmarks: category-to-product P@1 0.758, against 0.690 for general SigLIP and 0.673 for LAION CLIP ([Marqo](https://github.com/marqo-ai/marqo-FashionCLIP)). Those benchmarks test text-to-image and category retrieval, not same-item image matching, so they only suggest how the models would rank on this task. DINOv2 should be avoided without your own test. Even Zalando's best model was only **16–29% precise** on its own raw output. Expert reviewers, voting three to a pair, lifted that to 0.90–0.94, and crowd workers could not reach the 90% target ([arXiv 2403.11593](https://arxiv.org/html/2403.11593)). Embedding similarity therefore produces a shortlist, not a decision.

Cheaper image signals have their own failure modes. Perceptual hashes catch the same studio photo re-encoded or resized. They also produce false matches at Hamming distance 1 between unrelated products centred on white backgrounds ([arXiv 2605.21272](https://arxiv.org/pdf/2605.21272)), and plain tees on white backgrounds are exactly that case. Crops and mirrored images break them. A hash hit is strong evidence only together with a brand and colour agreement, and a miss is no evidence at all. Embeddings also under-represent colour ([arXiv 2503.09867](https://arxiv.org/pdf/2503.09867.pdf)), so two colourways of 528856 can embed almost identically. A masked dominant-colour check in Lab space works as a veto, though not as a reason to accept. For jerseys and graphic tees, reading discrete tokens (player name, number, sponsor, slogan) through OCR or a VLM is more decisive than any similarity score.

Vision-language models fit best as the last verification step. In the August 2026 "Retrieve, Match, Escalate" system, a cheap text cross-encoder auto-accepts at a calibrated **98% precision**. An agentic VLM that looks at images handles the ambiguous rest, which lifts coverage from **68% to 77%**. A self-hosted open-weight agent matched the frontier model's precision, at 88% versus 92% recall and about one-seventh of the cost ([arXiv 2608.25037](https://arxiv.org/abs/2608.25037)). VLMs have known blind spots for fine detail: commercial VLMs average 58% on simple visual tasks ([arXiv 2407.06581](https://www.alphaxiv.org/abs/2407.06581)). On plain basics they are also prone to "both are black crew-neck tees, same product". So let a VLM veto a match freely, but never let it be the only grounds for accepting a plain tee. Cost does not limit this. Gemini 3.1 Flash-Lite costs $0.25 per million input tokens and $1.50 per million output tokens, and the Batch API halves that ([Google AI pricing](https://aistudio.google.com/docs/pricing)). Assuming two images, attributes and a short verdict come to roughly 1–1.5k tokens per pair, one pair costs about $0.0005, and 50 pairs cost a few cents. The token count per image is an assumption, not a published figure.

## Search recall, not matching, sets the coverage ceiling

Searching marketplaces by code does not work in India. Flipkart's search for "puma 528856" returned unrelated Puma shoes ([Flipkart search](https://www.flipkart.com/search?q=puma+528856)). Myntra's numeric URLs use Myntra's own ID space, so a brand code can land on a different product ([Myntra](https://www.myntra.com/528856)). Amazon search blocked plain HTTP. Name-based search ranks the true item low: in the case that prompted this report, it came 14th on Flipkart and 7th on Myntra, so a top-5 or top-10 cutoff loses it before matching begins. Industrial systems avoid this by blocking on brand and then running nearest-neighbour search over their own crawled index. Even so, Zalando's best model put the true match at rank 1 only 84% of the time, against 95% within the top 3 ([arXiv 2403.11593](https://arxiv.org/html/2403.11593)). Candidate retrieval should be evaluated on its own, because anything it misses cannot be recovered later ([HackerNoon](https://hackernoon.com/why-your-llm-keeps-matching-the-wrong-products-and-why-a-better-prompt-wont-fix-it)).

For a live-search system, the fix is query quality and depth, not a better matcher. Build the queries from the brand-site canonical name and run several variants, the way product-search systems use LLM rewrites to widen the candidate pool ([TREC 2025 JBNU](https://trec.nist.gov/pubs/trec34/papers/JBNU.product.pdf); [arXiv 2602.23620](https://arxiv.org/html/2602.23620v1)):

- the canonical name plus colour ("puma train all day breathable training tee black men")
- the model line plus garment type
- the marketplace's own attribute template ("puma men round neck black t-shirt")
- the abbreviated form ("puma tad essential tee")

Fetch about 40 results for each variant, then deduplicate and rerank locally. On Myntra, use the brand-site name plus colour as the main query. On Amazon and Flipkart, a code read off a candidate's product page settles that candidate even if search ranked it 30th. Whether canonical-name queries actually lift the rank from 14th to the top few is the obvious next experiment and has not been measured. Searching the open web (for example `site:myntra.com`) and visual search are untested fallbacks.

## Industry accepts 40–60% coverage and buys precision with tiers and humans

No vendor claims high coverage in apparel. DataWeave puts apparel match rates at **40–60% versus 95% in electronics**. It attributes the gap to subjective similarity, fast-fashion churn, inconsistent size charts and noise from third-party sellers. It runs about 90% of decisions automatically through LLM attribute extraction and CLIP or Siamese image models, and sends the rest to specialist reviewers ([DataWeave](https://dataweave.com/blog/from-mess-to-match-solving-product-identity-at-retail-scale)). Its case studies report 75% on priority SKUs for a US fashion retailer, which it says beats a "fashion industry benchmark of 50%", and about 60% for Adidas/Reebok LATAM ([DataWeave case study](https://dataweave.com/pages/using-dataweaves-ai-powered-pricing-intelligence-for-fashion-ecommerce-retailer); [casestudies.com](https://www.casestudies.com/company/dataweave/case-study/adidas-customer-case-study)). These are unaudited vendor figures. "Match rate" (coverage) and "accuracy" (precision, claimed at 85–99%) are never defined consistently and should not be combined.

Vendors also split results into tiers rather than giving a yes or no. Intelligence Node distinguishes **exact**, **variant** and **similar** matches, and confirms similar matches with computer vision inside a price band ([Intelligence Node](https://www.intelligencenode.com/blog/product-matching-ai-for-ecommerce/)). Price2Spy advises matching at the most specific variant level, colour and size ([Price2Spy](https://www.price2spy.com/blog/?p=12445)). For a price or stock tracker, "same product" should mean the same brand, style and colourway (the full code, or the canonical name plus colour) and the same gender. Size is a variant to record, not part of identity. No Flipkart- or Myntra-authored paper on matching against other retailers was found. Their published work covers visual search and recommendation ([Flipkart arXiv 1703.02344](https://arxiv.org/pdf/1703.02344)).

## A five-stage cascade for 10–50 candidates per platform

The design below follows the evidence above. Code decides whenever it can, images rank, a VLM verifies a few pairs, and the system abstains on anything it cannot confirm. It runs once per source listing per target platform.

| Stage | What it does | Accept / reject rule | Cost |
|---|---|---|---|
| 0. Resolve | Read the source's code (Amazon Style Number/MPN, or Flipkart Style Code/Article Number) and validate it against the brand pattern. Look it up on the brand site to get the canonical name, colour name, gender, material, MRP and a reference packshot. Cache by code | If the source is on Myntra, resolve in reverse: search the brand site by Myntra's name and colour | 1–2 HTTP requests, cached |
| 1. Retrieve | Run 3–4 query variants per platform, about 40 results each, deduplicate to 10–50 candidates. Classify each fetch as OK, EMPTY or BLOCKED | A BLOCKED fetch yields "check failed", never "not listed" | 3–8 searches |
| 2. Identify | Fetch each candidate's product page on Amazon and Flipkart and extract the normalised code | Full-key equal → **exact**. Base equal, colour differs → **variant**. Both valid and base differs → reject | Page fetches, no model calls |
| 3. Veto and rank | Apply hard vetoes: brand (with alias map), gender, garment type, base colour, pack count, jersey team/season/kit. Rank survivors by max image cosine over all gallery pairs (FashionSigLIP or SigLIP), canonical-name token overlap, MRP equality, manufacturer-string equality and pHash reuse | Keep the top 3–5 above a calibrated floor. Apply a Lab-colour ΔE veto and an OCR/graphic-text veto for prints and jerseys | Local CPU/GPU embeddings |
| 4. Verify | Send the surviving pairs to a Flash-Lite-class VLM with both images and attributes. Ask for field-by-field verdicts quoting visible text, then SAME / DIFFERENT / UNSURE | Accept only SAME with no field conflict **and** at least one non-visual corroboration (name match, MRP plus manufacturer, or pHash reuse). Otherwise **not confirmed** | ≈$0.0005 per pair, a few cents per listing |

On Myntra, stage 2 has no code to read, so exact matches come from stages 3–4 instead. A brand-direct seller's name that matches the canonical name, plus the same base colour, MRP and manufacturer string, plus a VLM SAME is strong evidence. If any of these is missing, the result should be "variant" or "not confirmed". The Puma case passes on every one of these signals. A generic USPA polo from a third-party seller would correctly fail. Return the evidence with every decision: matched URL, the fields that matched, vetoed candidates and why, and fetch status. Price2Spy found that many apparent false positives were real matches the labellers had missed, so decisions need to be auditable ([Price2Spy](https://www.price2spy.com/blog/part-3-for-ml-experts-why-is-product-matching-so-difficult/)).

Calibrate before trusting any threshold. None of the starting values here is validated on Indian marketplace data: pHash ≤4 of 64 bits, the embedding floor and the ΔE cut-off. Build a labelled set of 300–500 pairs, balanced across exact matches, same-style-different-colour pairs and look-alike plain basics, and tune the auto-accept rule to about 98% precision, as the 2026 cascade did. Then report coverage separately for each platform pair and category. Accepted code-matched pairs become free training data, and a Zalando-style projection head trained on a few thousand of them is the cheapest upgrade available, from AUCPR 27 to 57–66 in Zalando's results.

## Conclusion

The Puma example looks like a hard text-matching problem, but very little of it needs text matching. Two of the three listings carry the answer in a structured field. The third carries the brand's own name, which only the brand's website can connect to that code. The core engineering work is extracting the code reliably, a per-brand bridge, and deep, well-formed searches, not a cleverer similarity model. Models matter only for Myntra, for brands without a bridge, and for unbranded basics. Those are also the cases where every published system, Zalando's included, either needs human review or still gets matches wrong.

For a small system, that means coverage depends on the brand mix more than on model quality. Puma-like brands that publish clean codes on their own sites should match with near-certainty. Licensee and house brands, plain basics and third-party resellers will fall into "not confirmed" at high rates, consistent with the 40–60% industry ceiling. Report coverage and precision per brand tier, not as one headline number.
